# MedNav 并发性能测试报告 v0.1

## 1. 结论

在单机本地环境、真实 PostgreSQL/Redis、Stub 临床模型与 Stub 地图服务的受控条件下，MedNav 症状 Run 链路使用 100 个独立 Session，连续执行三轮 60 秒固定速率测试：

> 在接入和 Stub Run 完成延迟 P99 均低于 500 ms、错误率低于 1% 的条件下，系统稳定承载 200 QPS。

三轮共提交 36,000 个 Run，全部返回 `202 Accepted`，并全部收到对应 SSE `RUN_FINISHED`；观测错误率为 0%。三轮中的最差接入 P99 为 331.44 ms，最差处理完成 P99 为 478.05 ms。

该结论是当前技术验证版本的本地短时稳态基线，不代表真实 OpenAI、Google Maps 链路的端到端容量，也不代表多实例生产环境容量。

## 3. 指标定义

- 接入延迟：从客户端提交 Run，到收到 HTTP `202 Accepted`。该路径包含用户消息持久化和 Session 入队。
- 处理完成延迟：从客户端提交 Run，到 SSE 收到对应 `RUN_FINISHED`。该路径包含 Stub 临床推理、结构化结果处理、Assistant 消息持久化和事件发布。
- 错误：网络错误、非 `202` 响应、`RUN_ERROR`，或者在 120 秒排空窗口内未收到 `RUN_FINISHED`。
- QPS：压测稳态窗口内成功接受的 Run 数除以实际发送时长。

## 5. 阶梯探索结果

500 QPS、250 个 Session、持续 30 秒的探索测试中，15,000 个 Run 全部完成且错误率仍为 0%，但接入 P99 为 1,765.75 ms、完成 P99 为 1,943.21 ms，未满足 500 ms 延迟 SLO。因此当前测试只能证明“已测试档位中 200 QPS 满足该 SLO”，不能宣称 200 QPS 是系统绝对容量上限。

高负载下主要表现为排队和长尾增加，而不是请求丢失。结合代码结构，后续应优先优化同步消息持久化、数据库连接池、无界 Session 调度线程池和批量写入。

## 6. 使用限制

1. 本测试隔离了 OpenAI 与 Google Maps。真实外部 API 的延迟、配额、429 和成本需要单独报告。
2. 60 秒乘三轮属于本地短时稳态测试，不等同于 30 分钟或数小时 Soak Test。
3. 负载发生器与应用位于同一主机，结果不包含公网或跨可用区网络延迟。
4. 当前应用为单实例，本报告不验证水平扩容、实例故障转移或跨实例 Session 有序性。
5. INFO 级逐 Run 同步日志会明显影响高负载测试，因此正式性能 Profile 使用 WARN；生产环境应采用异步、采样日志。

## 7. 简历建议表述

> 设计并实现 MedNav 固定速率并发压测工具，在隔离外部 API 性能变量、使用真实 PostgreSQL/Redis 的单机环境中，以 100 个并行 Session 连续执行三轮 60 秒测试；系统稳定承载 200 QPS，最差 P99 Run 完成延迟 478 ms，观测错误率 0%，并通过阶梯压测定位同步持久化导致的高负载长尾。

如需强调边界，面试时应说明该指标针对 Stub 临床推理链路；真实模型链路应使用完成延迟、429 比例、降级率、Token 成本和外部 API 配额作为独立指标。
